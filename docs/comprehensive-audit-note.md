### Robustness verdict
- bc-limit: design is sound (BCLM + config + hysteresis 86/85, writes only on state change, max 1 write/invocation, 60 s cadence, validates reads, verifies every write by read-back, never writes % to SMC). Fragility: no debounce, no confirmation read, no rate-of-change check — trusts a single ioreg read per invocation. Up-jump while holding → "nothing" (safe). Up-jump while charging → hold within 60 s (correct). Down-jump below lower (85) while holding → writes resume (BCLM=100); if the gauge recovers a minute later, it writes hold again — one 10→100→10 toggle pair per jump pair. Bounded by the 60 s cadence (cannot rapid-toggle), but gauge noise can drive real charge/resume cycles. The 1% hysteresis band (86/85) is narrower than the observed gauge noise (±7–12%), so the band can be crossed in a single step.
- bc-watchdog: the live 19:00 jump was handled correctly (LAYER3 drift did not false-fire; the ladder stayed healthy; no notification; no config rewrite; no BCLM write). LAYER3's 300 s wait is an accidental debounce (a dip below lower only triggers reapply+notify after 300 s of persistence). LAYER2 overshoot is the real fragility: it fires correctly per its rule (PCT 93 > 88) but cannot distinguish a gauge artifact from real overcharge. The episode is now stuck: PCT stays 93 indefinitely on AC hold, so it logs every tick while APG-paused and .overshoot_state persists. Harmless in v1 (no forced discharge — action is hold-and-wait), but it would misfire a future forced-discharge mechanism (it would discharge a battery that is not actually overcharged). The 120 s post-wake delay protects the discharge path from wake-jumps. Single ioreg snapshot per tick; skips the tick if unreadable (good), but acts on a readable-but-wrong % with no smoothing.
- bc-status / plugin: display-only — the jump just changes the shown % (86→93). Hold-reached notification is keyed by limit (86/85, pre-seeded) — no re-notification on the jump. Fine. (Note: no bc-status.c source exists in the repo — only status_prototype.c — so its exact % formula wasn't re-verified; its output matches ioreg within rounding, 86.1% vs 86.)
- Overall verdict: CORRECT on the observed jump, FRAGILE by design — the tool trusts single % reads with no jump detection, and LAYER2 cannot tell artifact from overcharge.
- Fixes applied (helpers W1): gauge-jump deferral in the watchdog ladder (prev-PCT tracking, ≥5%/tick defers one ladder increment). Proposed (not applied — needs a build decision): bc-limit confirm-before-write (require a threshold-crossing reading to be confirmed by a second ioreg read ~5–10 s later, or two consecutive invocations, before writing; log "jump suspected" when |Δ%| ≥ 5% in one 60 s interval). Required before any forced-discharge work: LAYER2 must require a second confirming signal (IsChg=Yes, Amperage>0, or CurrentCapacity rising across two ticks) before treating PCT>UPPER+2 as real overcharge.
